# Pelagos D9.4 Increment 3 — Coordinated GUI Maritime Routing Integration (ROUT-005)

## 1. Purpose and Scope

This specification documents the implementation and operational verification of **Increment 3: Coordinated GUI Maritime Routing** for Milestone D9.4.

Increment 3 bridges the operational backend routing engine and compiled MARNET graph artifact with the application's HTTP API and CesiumJS 3D frontend interface.

> [!WARNING]
> **Navigational Disclaimer:** Pelagos maritime routing provides macro-corridor voyage distance calculations and path visualization on a generalized graph network. Straight-line port connectors are approximations, not verified navigable channels. The system is strictly **NOT** certified for real-world navigational passage planning, safety of life at sea, collision avoidance, or ECDIS electronic navigation.

## 2. Architecture and Data Flow

```
+-----------------------------------------------------------------------------------------+
|                                    GUI & API DATA FLOW                                  |
+-----------------------------------------------------------------------------------------+
       [ CesiumJS 3D Globe / Directions Layer ] (gods-eye-view-main/src/layers/directions)
            |
            | User selects "SEA" mode and picks Origin (A) and Destination (B) on globe
            |
            | POST /api/v1/routing/calculate
            | Body: { origin, destination, canal_policy: "allow", routing_mode: "marnet", supports_segments: true }
            v
       [ Vite Development Proxy ] (port 5173 -> proxies /api/v1 to http://127.0.0.1:8000)
            |
            v
       [ FastAPI Application ] (backend/pelagos/api/routes/routing.py)
            |
            | Dependency: get_routing_engine() (lazy MARNET graph cache loader)
            v
       [ Maritime Routing Engine ] (backend/pelagos/routing/service.py)
            |
            | - Geodesic nearest-node snapping (< 50 NM threshold)
            | - Polar boundary rejection (|lat| >= 66.5 deg)
            | - Dijkstra / Bidirectional A* over 14,988 MARNET edges
            | - Antimeridian detection and polyline splitting
            v
       [ RoutingResult Response ]
            | - status: "calculated" | "unsupported_route" | "invalid_input" | "configuration_error"
            | - distance_nm, distance_km, canals_transited, snap distances
            | - geometry_segments: [[[lon, lat], ...], [[lon, lat], ...]]
            v
       [ CesiumJS Multi-Segment Polyline Renderer ]
            | - Renders each segment as distinct polyline entity (directions:route:segment_N)
            | - Strictly prevents antimeridian cross-globe chord artifacts
            | - On failure: clears stale graphics and displays honest error message
+-----------------------------------------------------------------------------------------+
```

## 3. Backend HTTP API Contract

Mounted at `/api/v1/routing`:

### 3.1 `POST /api/v1/routing/calculate`
- **Request Schema (`RoutingRequest`):**
  ```json
  {
    "origin": { "coordinates": [4.4, 51.9] },
    "destination": { "coordinates": [103.8, 1.25] },
    "canal_policy": "allow",
    "routing_mode": "marnet",
    "supports_segments": true
  }
  ```
  - `canal_policy`: `"allow"` | `"avoid_panama"` | `"avoid_suez"` | `"avoid_all"`
  - `routing_mode`: `"marnet"` | `"prototype"`
  - `supports_segments`: `true` (enables antimeridian splitting into `geometry_segments`) | `false` (suppresses antimeridian routes with `unsupported_route`)
- **Response Schema (`RoutingResult`):**
  - Success (`status="calculated"`): Returns `summary`, `geometry`, `geometry_segments`, `origin_snapping`, and `destination_snapping`.
  - Failure (`status="unsupported_route"` | `"invalid_input"` | `"configuration_error"`): Returns strictly empty `geometry: []`, empty `geometry_segments: []`, and descriptive `error_message`.
- **Fail-Closed Guarantees:**
  - If the MARNET graph cache is missing or corrupt, returns `status="configuration_error"` without silent fallback to prototype mode.
  - If an endpoint is inland (> 50 NM from graph), returns `status="unsupported_route"`.
  - If an endpoint reaches polar waters ($|\text{latitude}| \ge 66.5^\circ$), returns `status="unsupported_route"`.

### 3.2 `GET /api/v1/routing/health`
- Reports routing engine health and MARNET cache availability without loading the graph into memory at application boot.

## 4. Frontend Directions Integration

### 4.1 Mode Selection
- Registered `SEA` chip (`chip: 'SEA'`, `word: 'Sea (MARNET)'`, `icon: '🚢'`) alongside existing land modes (`car`, `foot`, `bike`).
- Land routing behavior, OSRM request structures, and default modes are completely preserved with zero regressions.

### 4.2 Multi-Segment Polyline Rendering
- When `geometry_segments` contains multiple LineStrings (e.g. crossing the 180° antimeridian between Seattle and Yokohama), the layer creates separate Cesium polyline entities:
  - `directions:route:segment_0`
  - `directions:route:segment_1`
- Prevents flattening disjoint coordinates into a single polyline, eliminating cross-globe visual chords.
- For single continuous routes, creates `directions:route`.

### 4.3 Deterministic Lifecycle & Cleanup
- `clearRouteGraphics()` deterministically removes all route entities from the Cesium entity collection.
- Stale route graphics are immediately cleared when a request fails, when non-calculated statuses are received, or when endpoints change.

### 4.4 Summary Statistics & Honest Limitations
- Displays nautical miles (`distanceNm`) formatted with comma separators, metric kilometers (`distanceKm`), transited canals (`Suez`, `Panama`), and port snap distances (`snap ~X.X NM`).
- Straight-line port connectors are documented in user statistics as approximate connectors, not certified channels.

## 5. Startup Prerequisites and Verification Commands

> [!NOTE]
> Distinguish automated test suite success from an interactive live GUI session. The automated test suite validates all request schemas, calculations, segment parsing, and entity lifecycles headlessly. Live interactive manual verification requires launching both the FastAPI backend and the Vite frontend.

### 5.1 Automated Test Execution (Headless)

1. **Backend Routing and API Test Suite:**
   ```powershell
   # Run all 82 routing engine, ingestion, and API tests
   $env:PELAGOS_MARNET_INTEGRATION="1"
   pytest tests/test_routing_engine.py tests/test_marnet_routing.py tests/test_marnet_ingestion.py tests/test_marnet_integration.py tests/test_routing_api.py -v
   ```
2. **Frontend Directions Unit Tests:**
   ```powershell
   cd gods-eye-view-main
   node --test src/data/directions.test.mjs src/data/directionText.test.mjs
   ```

### 5.2 Interactive GUI Launch Instructions

To launch the live application for visual testing:

1. **Terminal 1: Start FastAPI Backend Server**
   ```powershell
   # Ensure local cache exists: .cache/pelagos/routing/marnet_network.json
   # If not generated, run: python scripts/ingest_marnet.py
   python -m uvicorn backend.pelagos.api.main:app --host 127.0.0.1 --port 8000
   ```
   *Verify backend readiness:* Navigate to `http://127.0.0.1:8000/api/v1/routing/health` (should return `{"status": "ok", "marnet_cache_available": true}`).

2. **Terminal 2: Start CesiumJS Frontend Server**
   ```powershell
   cd gods-eye-view-main
   npm run dev
   ```
   *Verify proxy connection:* Open browser at `http://localhost:5173`. Vite automatically proxies `/api/v1` calls to `http://127.0.0.1:8000`.

## 6. Step-by-Step GUI Acceptance Checklist

Follow this checklist during interactive manual testing in the CesiumJS browser console:

### Scenario A: Standard Maritime Route (Rotterdam to Singapore)
1. Open the Directions tool panel by clicking the compass icon (🧭).
2. Click the `SEA` mode chip.
3. Click point **A** near Rotterdam (approx. `51.9° N, 4.4° E`).
4. Click point **B** near Singapore (approx. `1.25° N, 103.8° E`).
5. **Expected Outcome:**
   - Polyline renders in cyan flowing dashes through the English Channel, Gibraltar, Mediterranean Sea, Suez Canal, Red Sea, Indian Ocean, and Malacca Strait.
   - Status bar displays: `~8,409.8 NM (15,575 km) via Sea (MARNET) • Suez, Malacca • snap ~10.5 NM`.
   - No error toasts or straight-line inland shortcuts appear.

### Scenario B: Antimeridian Route (Seattle to Yokohama)
1. Click `CLEAR` to reset current route and markers.
2. Ensure `SEA` mode chip is active.
3. Click point **A** near Seattle / Puget Sound (approx. `47.6° N, -122.4° W`).
4. Click point **B** near Yokohama / Tokyo Bay (approx. `35.4° N, 139.7° E`).
5. **Expected Outcome:**
   - Route computes across the North Pacific.
   - The route is rendered as **two separate disjoint polyline entities** (`directions:route:segment_0` and `directions:route:segment_1`) terminating at $-180^\circ$ and $+180^\circ$.
   - **Crucial Check:** The globe does NOT display a horizontal streak or chord cutting backwards through North America, the Atlantic, and Eurasia.
   - Status bar displays: `~4,260 NM (7,890 km) via Sea (MARNET)`.

### Scenario C: Rejected / Polar / Landlocked Route
1. Click `CLEAR`.
2. Ensure `SEA` mode chip is active.
3. Click point **A** in deep inland North America (e.g. Denver, Colorado: `39.7° N, -104.9° W`).
4. Click point **B** in Western Europe.
5. **Expected Outcome:**
   - Request returns `status="unsupported_route"` (endpoint exceeds 50 NM snapping threshold).
   - Graphic polylines are immediately cleared.
   - Status bar / toast displays honest failure message: `Origin coordinates exceed maximum port snapping threshold (50.0 NM)`.
   - Repeat with a high-latitude polar point ($> 66.5^\circ\text{ N}$): Status displays `Route traverses polar waters (|latitude| >= 66.5)`.
