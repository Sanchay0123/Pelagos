# Operational Maritime Routing Foundation Stage 3 Design and Test Plan (ROUT-004)

## 1. Purpose and Executive Summary

This document establishes the revised architectural design, service configuration contract, port snapping specification, route failure semantics, API schema evolution, and verification test plan for **Stage 3** of the Pelagos Operational Maritime Routing subsystem.

### 1.1 Context and Baseline
In Milestone D9.2 ([commit `1780234`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos)), a prototype routing engine was established based on a synthetic, manually authored 57-node macro-corridor fixture. Milestone D9.3 ([ROUT-002](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/docs/routing/D9.3-real-network-data-investigation.md)) investigated upstream Eurostat SeaRoute MARNET assets. Milestone D9.4 Increment 1 ([ROUT-003](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/docs/routing/D9.4-implementation-plan.md), [commit `4ffaa1a`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos)) implemented fail-closed acquisition tooling (`scripts/ingest_marnet.py`) and a deterministic graph compiler (`backend/pelagos/routing/ingestion.py`), compiling the inspected 50 km MARNET dataset into a verified local cache artifact (`.cache/pelagos/routing/marnet_network.json`) of 7,390 nodes and 15,423 edges.

### 1.2 Objective of Stage 3 Increment 2 Final Corrective Pass (v1.4.0)
This increment addresses the findings of the Increment 2 code-review audit:
1. **Symmetric Polar Boundary Exclusion:** Replaces one-sided northern Arctic filtering with an explicit symmetric **Arctic and Antarctic Circle exclusion** ($|\text{latitude}| \ge 66.5^\circ$). Empirically excludes 435 polar edges (433 Arctic edges and 2 Antarctic edges reaching $-70.0^\circ\text{ S}$ and $-80.0^\circ\text{ S}$), leaving 14,988 navigable edges. Fails closed on missing or malformed geometry and rejects endpoints at or beyond either boundary ($\pm 66.5^\circ$). Explicitly documents that this provisional boundary does not guarantee the absence of seasonal sea ice, pack ice, or navigation hazards at lower sub-polar latitudes.
2. **Cache Integrity Lifecycle Specification:** Defines and proves the verified in-memory graph cache lifecycle. Manifest schema, transformation version, SHA-256 checksum, and file size are validated strictly at initialization. A running engine operates from its validated in-memory snapshot; disk mutations do not alter running instances. A newly initialized engine rejects altered disk artifacts with `status="configuration_error"`. Invalid or missing MARNET artifacts never trigger silent fallback to prototype routing.

> [!IMPORTANT]
> **Scope Boundary:** This document is an architectural design and test specification only. In accordance with project instructions, no CesiumJS frontend changes or external dataset downloads are performed. Prototype mode and its regression behavior are strictly preserved.

## 3. Dual-Mode Routing Configuration Contract

To isolate the synthetic test fixture from operational candidate assets without coupling or silent failures, Stage 3 defines an explicit dual-mode configuration contract.

### 3.1 Mode Definitions

```
                     +---------------------------------------+
                     |         RoutingRequest                |
                     |  - origin: PortIdentifierOrCoords     |
                     |  - destination: ...                   |
                     |  - routing_mode: "prototype" | "marnet"|
                     +-------------------+-------------------+
                                         |
                                         v
                     +---------------------------------------+
                     |        MaritimeRoutingEngine          |
                     |  - Default: PELAGOS_ROUTING_MODE      |
                     +-------------------+-------------------+
                                         |
                +------------------------+------------------------+
                |                                                 |
                v (mode="prototype")                              v (mode="marnet")
  +-------------------------------+             +----------------------------------+
  |    PrototypeMaritimeGraph     |             |        MarnetMaritimeGraph       |
  |  - Source: sea_lanes.json     |             |  - Source: .cache/.../network.json|
  |  - 57 nodes, 58 edges         |             |  - 7,390 nodes, 15,423 edges     |
  |  - Synthetic test fixture     |             |  - 50 km generalized Eurostat    |
  |  - 100% offline, zero cache   |             |  - Requires verified local cache |
  +-------------------------------+             +----------------------------------+
```

1. **`prototype` Mode (Default):**
   - Loads the committed, synthetic macro-corridor fixture ([`sea_lanes.json`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/backend/pelagos/routing/fixtures/sea_lanes.json)).
   - Serves as the zero-dependency test foundation.
   - Guaranteed to work on clean checkouts without external cache assets or internet access.
2. **`marnet` Mode (Operational Candidate):**
   - Loads the local, Git-ignored compiled graph artifact ([`.cache/pelagos/routing/marnet_network.json`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/.cache/pelagos/routing/marnet_network.json)).
   - Operates over 7,390 nodes and 15,423 edges with geodesic weights.
   - Requires verified local cache populated via `scripts/ingest_marnet.py`.

### 3.2 Configuration Precedence
- **System-Level Default:** Controlled by environment variable `PELAGOS_ROUTING_MODE` (values: `'prototype'`, `'marnet'`). If unset, defaults strictly to `'prototype'` to maintain zero-setup developer and CI execution.
- **Per-Request Override:** The `RoutingRequest` schema is augmented with an optional field:
  ```python
  routing_mode: Optional[str] = Field(
      default=None,
      description="Routing graph mode: 'prototype' (synthetic fixture) or 'marnet' (locally compiled 50 km network). If null, defaults to system configuration.",
  )
  ```
- If `request.routing_mode` is provided, it takes precedence for that individual calculation.

### 3.3 Strict Fail-Closed Rule (No Silent Fallback)
> [!CAUTION]
> **Zero Silent Fallback Mandate:** If `routing_mode="marnet"` is selected and the local cache artifact is missing, corrupted, unvalidated, or schema-incompatible, the engine MUST fail closed and return `status="configuration_error"`. Under NO circumstances may the engine silently fall back to `prototype` mode.

A silent fallback would conceal configuration failures, invalidate benchmark comparisons, and violate provenance integrity by returning synthetic routes under the guise of the 50 km maritime network.

### 3.4 Startup and Request Isolation
- **Zero Startup Downloads:** The routing service and FastAPI application MUST NEVER attempt to download, fetch, or scrape upstream assets during startup or while servicing API requests.
- **Startup Configuration Validation:**
  - If `PELAGOS_ROUTING_MODE=marnet` is configured in the environment, application startup executes an offline cache verification check during FastAPI `lifespan` startup.
  - If `.cache/pelagos/routing/marnet_network.json` or `manifest.json` is missing or corrupted, the service logs a `CRITICAL` error and marks `is_marnet_ready = False`.
  - In non-strict mode, the application continues running to allow health checks and prototype requests, but rejects MARNET queries with `status="configuration_error"`.
- **Request-Time Validation:**
  - When an individual request arrives with `routing_mode="marnet"`, the engine verifies that `is_marnet_ready == True`.
  - If unready, it returns `status="configuration_error"` immediately with an actionable error message, without attempting graph execution or any network calls.

## 4. Port Snapping Architecture and Constraints

### 4.1 Evaluation of the 50.0 NM Provisional Maximum
Milestone D9.2 used an arbitrary `max_distance_nm = 250.0` for prototype testing. In Stage 3, a **50.0 NM** threshold is proposed as a **provisional maximum**, NOT an empirically validated global truth.

#### 4.1.1 Network Generalization vs Node Spacing
- MARNET is described upstream as a "50 km generalized network." This designation refers to the spatial resolution and Douglas-Peucker simplification tolerance used to filter the underlying AIS/ORNL line features.
- It does **not** guarantee a uniform 50 km (27 NM) distance between every adjacent graph node.
- In coastal, littoral, and chokepoint areas (e.g. English Channel, Strait of Malacca), nodes are spaced 3 to 15 NM apart. In open ocean basins (e.g. South Pacific, Indian Ocean), edge segments extend 50 to 120 NM between vertices.
- Therefore, a snapping threshold cannot be derived purely from the "50 km" moniker; it must be treated as an operational trade-off between fairway reach and land-crossing risks.

#### 4.1.2 Comparison of Provisional Snapping Thresholds

| Provisional Snapping Radius | Technical Implications | Evaluation |
| :--- | :--- | :--- |
| **< 20 NM** | Disconnects major global ports whose fairway access gates lie in deep water 20–35 NM offshore (e.g., Rotterdam Eurogeul pilot buoy is ~22 NM offshore; New Orleans Southwest Pass approach is ~28 NM offshore). | **Too strict:** Disconnects valid commercial ports. |
| **50.0 NM (Provisional Ceiling)** | Reaches deep-water access gates for coastal ports while rejecting inland and landlocked coordinates. However, it risks snapping across narrow peninsulas if unconstrained. | **Provisional Maximum:** Acceptable starting threshold subject to empirical registry validation. |
| **> 100 NM** | High risk of geometric artifacts, snapping across large peninsulas (e.g. Tampa to Atlantic across Florida) or connecting landlocked lakes to offshore lanes. | **Unacceptable:** Introduces false navigability across landmasses. |

#### 4.1.3 Required Evidence for Empirical Validation
Before 50.0 NM (or any other threshold) can be accepted as a production standard, the following empirical evidence must be gathered:
1. **Port Registry Snapping Distribution:** Calculate geodesic distance from all coordinates in [`ports.json`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/backend/pelagos/routing/fixtures/ports.json) (and full UN/LOCODE fixtures) to the nearest MARNET node. Record mean, median, 95th percentile, and maximum distances.
2. **Landmass Intersection Audit:** For every snapped port connector, evaluate whether the straight-line segment intersects global shoreline polygons (e.g. Natural Earth 10m coastline). Connectors crossing land must be rejected regardless of distance.
3. **Approach Channel Correctness:** Verify that the snapped graph node actually leads into the intended navigational fairway, rather than an adjacent bay or reverse side of a barrier island separated by shallow water.

### 4.2 Nearest-Node Calculation: Geodesic Scan Baseline and Conditional Indexing

#### 4.2.1 Reference Correctness Baseline: Complete Geodesic Scan
- MARNET contains 7,390 nodes. In pure Python using `pyproj.Geod.inv`, a brute-force scan over all 7,390 coordinates executes in approximately 12 to 18 ms per query. Using vectorized NumPy/PyProj, this drops to $< 2\text{ ms}$.
- **Stage 3 Baseline Decision:** The reference implementation will use a **complete geodesic nearest-node scan** as the primary correctness baseline.
- **Rationale:** A full scan has zero boundary edge cases, avoids false negatives at bounding-box edges (especially near the antimeridian or poles), requires zero spatial index memory overhead, and provides an unambiguous ground truth for testing.

#### 4.2.2 Conditional Spatial Indexing
- Spatial indexing (e.g., bounding-box pre-filtering or a spherical KD-Tree) will **only** be implemented if measured production latency profiling demonstrates that the complete geodesic scan is an actual bottleneck under expected query loads.
- If profiling warrants spatial indexing, the index must be validated against the full geodesic scan to ensure 100% result concordance.

### 4.3 Nature of Snapped Connectors
> [!WARNING]
> **Connector Semantics:** A snapped connector is strictly a **geometric straight-line approximation between a fairway point and the offshore grid**, NOT a certified navigable channel, bathymetric track, or pilotage passage.

- Snapped connectors must be explicitly isolated from network edges.
- Waypoint sequence must tag connectors distinctly: `waypoint_type: "port_connector_approximation"`.
- Distances must be disaggregated in `RouteSummary`:
  $$\text{total\_distance\_nm} = d_{\text{origin\_connector}} + d_{\text{graph\_network}} + d_{\text{dest\_connector}}$$
  where $d_{\text{origin\_connector}}$ and $d_{\text{dest\_connector}}$ are reported independently so consumers can inspect the exact off-grid distance.

### 4.4 Port Coordinate Confidence and Deferral of Fairway Matching
The port registry ([`ports.json`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/backend/pelagos/routing/fixtures/ports.json)) assigns each port a `coordinate_type`. Snapping behavior depends on this classification:
1. `verified_marine_access_point`: High confidence (e.g. Rotterdam Eurogeul pilot buoy). Permitted to snap up to provisional 50.0 NM.
2. `approximate_marine_access_point`: Medium confidence (e.g. Southwest Pass entrance). Permitted to snap up to provisional 50.0 NM; limitations array notes approximate access.
3. `unverified_marine_access_point`: Low confidence. Permitted to snap; limitations array includes explicit warning that coordinates are unverified test points.
4. `port_point` / `administrative_point`: City center or land-based administrative centroids. If distance to nearest marine node exceeds 10.0 NM, or if the connector crosses land, the engine must flag an invalid endpoint or reject routing.

> [!IMPORTANT]
> **Formal Deferral of `fairway_match`:** Previous drafts proposed an `is_direct_fairway_match` boolean. Because Pelagos currently lacks an authoritative global dataset of fairway pilot buoys, approach channel gates, and port entry polygons, **promising a `fairway_match` result is formally deferred**. No such field will be exposed in the API until an authoritative fairway fixture and spatial matching algorithm are implemented and tested.

## 5. Passage Metadata, Policy, and Failure Semantics

### 5.1 Passage Attribute Reconciliation
An inspection of the active codebase and compiled artifacts reveals differing nomenclature across components:
- In `marnet_plus_50km.gpkg` (SQLite table `type`): Column is named `pass`.
- In `pass.gpkg` (SQLite table `pass`): Column is named `id`.
- In compiled `.cache/pelagos/routing/marnet_network.json`: Edge attribute is serialized as `pass_id`.
- In prototype fixture `sea_lanes.json`: Edge attribute is serialized as `canal`.

#### Normalization and Handling Rules:
1. **Attribute Normalization:** The Stage 3 graph loader will normalize all passage identifiers to a standardized internal edge attribute `pass_id: Optional[str]`.
2. **Canonical Vocabulary:** The 12 recognized passages from Eurostat SeaRoute are:
   `{"panama", "suez", "dover", "gibraltar", "malacca", "bering", "magellan", "northwest", "babelmandeb", "kiel", "corinth", "northeast"}`.
3. **Missing and Null Values:** In SQLite, features without passage tags have `pass = NULL`. These are normalized to `pass_id = None`. Empty strings or whitespace-only strings are normalized to `None`.
4. **Unknown Passage Tags:** If an edge in a future dataset contains a passage tag not in the canonical vocabulary, it will be retained as-is in edge metadata, logged with a `WARNING`, and will **not** be automatically masked unless an explicit policy rule targets it.

### 5.2 Canal Avoidance Policy and Empirical Alternative Path Proofs
- `canal_policy = "allow"`: All edges navigable.
- `canal_policy = "avoid_panama"`: Edges where `pass_id == "panama"` are suppressed via `nx.subgraph_view`.
- `canal_policy = "avoid_suez"`: Edges where `pass_id == "suez"` are suppressed.
- `canal_policy = "avoid_all"`: Both Panama and Suez are suppressed.

#### 5.2.1 Recorded Empirical Graph-Query Evidence

#### 5.2.2 Critical Geographic Grounding of Alternative Paths
1. **Cape of Good Hope Bypass Grounding:**
   The `avoid_suez` route between Rotterdam and Singapore reaches $-35.00^\circ\text{ S}$ at longitudes $17.26^\circ\text{ E}$ to $22.30^\circ\text{ E}$. This coordinate sequence physically passes south of Cape Agulhas ($34.83^\circ\text{ S}, 20.00^\circ\text{ E}$) and Cape of Good Hope ($34.35^\circ\text{ S}, 18.47^\circ\text{ E}$), fully validating the geographic description of a South African Cape bypass.
2. **Correction of the "Cape Horn / Drake Passage" Claim:**
   Previous drafts claimed that `avoid_all` between New Orleans and Japan routes via Cape Horn or the Strait of Magellan. **This claim was factually incorrect.**
   - The Dijkstra shortest path under `avoid_all` actually routes eastward across the Atlantic, rounds South Africa (latitude $-35.00^\circ\text{ S}$), and crosses the Indian Ocean to Japan at **15,630.0 NM**.
   - If forced westward around South America (by suppressing African coordinates), a connected path through the Strait of Magellan (`pass_id == "magellan"`, min latitude $-53.94^\circ\text{ S}$) does exist in MARNET at **16,751.7 NM**.
   - However, because the eastward African route is 1,121.7 NM shorter, unconstrained Dijkstra will never select the Magellan/Cape Horn route for this port pair.
   - **Conclusion:** `avoid_all` must be described strictly as a **graph-computed alternative path excluding both canals**. Dedicated commercial validation of a Cape Horn bypass remains formally pending.
3. **Enforcement Rules:**
   - If an avoidance constraint is requested and no alternative path exists, the engine must return `status="unsupported_route"`; under NO circumstances may the avoidance policy be silently ignored.
   - The returned waypoint sequence must be verified to contain zero edges tagged with the avoided passage identifier.

### 5.3 Demonstrable Polar-Route Exclusion and Formal Policy Deferral

#### 5.3.1 Investigation of Ingestion Geometry Preservation
To determine whether complete source LineString geometry is preserved or discarded:
1. **Geometry Retention in Artifact:** Inspection of [`backend/pelagos/routing/ingestion.py`](file:///c:/Users/Lenovo/Desktop/random%20codes/SIH26/Pelagos/backend/pelagos/routing/ingestion.py#L502-L585) confirms that `WkbGeometryParser.parse_gpkg_linestring` unpacks every point in the OGC WKB LineString blob.
2. **Intermediate Vertices Preserved:** Intermediate vertices are utilized to sum exact WGS84 geodesic lengths (`MarnetGraphBuilder.calculate_linestring_length_nm`) AND are preserved verbatim on the NetworkX edge (`geometry=best_feat["points"]`).
3. **Artifact Serialization:** In `.cache/pelagos/routing/marnet_network.json`, every edge object contains an explicit `"geometry": [[lon, lat], ...]` array. Exactly 636 edges contain $>2$ vertices.
4. **No Pruning/Simplification:** The ingestion pipeline performs no Douglas-Peucker simplification, coordinate decimation, or vertex pruning during export. All vertices are preserved at 6 decimal places.

#### 5.3.6 Enforceable Symmetric Polar Boundary and Navigational Limitations
1. **Symmetric Exclusion Rule:** Comprehensive polar exclusion evaluates all geometry vertices across both hemispheres:
   $$\text{Reject edge if } \exists (x, y) \in \text{geometry}(u, v) \text{ such that } |y| \ge 66.5^\circ$$
2. **Endpoint Validation:** Endpoint coordinates with $|\text{lat}| \ge 66.5^\circ$ are rejected at the service boundary with `status="unsupported_route"`.
3. **Fail-Closed Geometry Validation:** If an edge's geometry is missing, empty, malformed (fewer than 2 points, non-numeric, `NaN`, or `Inf`), the evaluator fails closed (`is_polar_edge() == True`), preventing invalid edges from entering the navigable graph.
4. **Navigational Limitations Disclaimer:**
   - **Operational polar routing is formally DEFERRED.**
   - The provisional $\pm 66.5^\circ$ boundary defines the formal Arctic and Antarctic Circle exclusion. **It does NOT guarantee the absence of seasonal sea ice, pack ice, icebergs, or severe maritime hazards at lower sub-polar latitudes** (such as the Southern Ocean, Drake Passage, Sea of Okhotsk, Baltic Sea, or Gulf of St. Lawrence).
   - Any route query whose candidate path or endpoints touch or cross $|y| \ge 66.5^\circ$ fails closed:
     ```json

       "status": "unsupported_route",
       "error_message": "Route traverses polar waters (|latitude| >= 66.5; Arctic or Antarctic Circle); rejected because comprehensive ice and hydrographic clearance cannot be verified."
     }
     ```

### 5.6 Cache Integrity Lifecycle and In-Memory Snapshot Isolation
To ensure high performance, thread safety, and deterministic execution without per-query disk overhead, the MARNET graph cache follows an explicit lifecycle:
1. **Verification at Initialization:**
   - Manifest existence, JSON syntax, `schema_version == "pelagos-marnet-graph-v1"`, and `transformation_version == "1.0.0"` are verified.
   - Compiled artifact file size matches manifest `size_bytes`.
   - Artifact content SHA-256 checksum matches manifest `sha256`.
   - If any verification check fails, initialization raises `MarnetCacheError` and the service returns `status="configuration_error"`.
2. **In-Memory Snapshot Execution:**
   - Upon successful validation and graph compilation, the running `MaritimeRoutingEngine` stores the parsed `MarnetMaritimeGraph` instance in memory.
   - All subsequent routing requests are resolved against this in-memory graph snapshot without disk re-reading or per-query cryptographic re-hashing.
3. **Disk Modification and Restart Semantics:**
   - Modifications, corruptions, or deletions of the disk artifact files (`manifest.json` or `marnet_network.json`) that occur while the engine is running do **not** affect the active in-memory graph snapshot. The running engine does not poll or watch disk files.
   - Any newly initialized engine instance (or service process restart) performs full integrity re-verification against the disk cache and immediately fails closed with `status="configuration_error"` if disk files were altered or corrupted.
4. **Zero Fallback Guarantee:**
   - Under no circumstances does a missing, invalid, or corrupted MARNET cache trigger silent fallback to prototype routing. If `routing_mode="marnet"` is requested, failures return `status="configuration_error"` with strictly empty geometry.

### 6.2 Antimeridian-Safe Geometry Semantics
The API defines exact semantics for `geometry` and `geometry_segments`:

1. **Unsupported or Failed Routes (`status != "calculated"`):**
   - `geometry = []`
   - `geometry_segments = []`
   - Both are strictly empty. No chord, connector, or partial polyline is ever emitted.
2. **Standard Calculated Routes (No Antimeridian Crossing):**
   - `geometry = [[lon_1, lat_1], [lon_2, lat_2], ..., [lon_N, lat_N]]`
   - `geometry_segments = [[[lon_1, lat_1], [lon_2, lat_2], ..., [lon_N, lat_N]]]`
   - `geometry_segments` contains exactly one polyline segment identical to `geometry`.
3. **Antimeridian-Crossing Routes (e.g. Seattle to Yokohama):**
   - The path traverses a zero-weight bridge edge connecting $[180.0, \phi]$ and $[-180.0, \phi]$.
   - `geometry_segments` splits at the bridge into distinct disjoint polylines:
     - Segment 1: `[[lon_origin, lat_origin], ..., [180.0, phi]]` (Eastern Pacific / Western Hemisphere).
     - Segment 2: `[[-180.0, phi], ..., [lon_dest, lat_dest]]` (Western Pacific / Eastern Hemisphere).
   - `geometry`: To prevent uncoordinated legacy clients from drawing a horizontal wrap-around chord across continents, `geometry` is set to `[]` unless `supports_segments == True`.

### 6.3 Concrete Frontend Rollout Strategy and Safety Boundary

> [!CRITICAL]
> **Safety Boundary Mandate:** A backend-only implementation MUST NOT be described as fully antimeridian-safe while the active frontend remains incompatible. Emitting a text warning does NOT prevent CesiumJS or 2D renderers from drawing visual wrap-around chords.

#### Concrete Rollout Decision:
Pelagos adopts **Strategy 1 (Coordinated Backend & Frontend Rollout) with Strategy 2 (Interim Safety Interlock)**:
