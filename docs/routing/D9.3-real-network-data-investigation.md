# Pelagos Real Maritime Routing Network Data Investigation (Eurostat MARNET)

## 1. Executive Summary and Finding

### Finding: Conditionally Ready (Awaiting Project Overseer Review)

The investigation into acquiring and integrating an authentic navigable maritime routing network into Pelagos has evaluated the canonical upstream **Eurostat SeaRoute MARNET** dataset. The dataset was retrieved, unpacked, and analyzed in an isolated temporary environment outside the Git workspace (`<scratch_dir>/`).

Eurostat MARNET is **a generalized maritime shipping-lane network**, developed primarily for statistical macro-voyage estimations by the European Commission. It is **not** an Electronic Chart Display and Information System (ECDIS) hydrographic database, does **not** contain bathymetric depth soundings or under-keel clearance guarantees, and does **not** establish real-world navigability for individual vessels.

The investigation finds that Eurostat MARNET is **empirically and structurally viable** for macro-level maritime routing in Pelagos, but integration remains **conditionally ready** subject to four specific technical, legal, and operational prerequisites:

1. **Antimeridian Coordinate Bridging**: Upstream planar GIS geometries terminate at the 180th meridian ($[-180.0^\circ, +180.0^\circ]$). Standard graph loaders treat $+180.0^\circ$ and $-180.0^\circ$ as disconnected nodes, severing trans-Pacific connectivity. Ingestion requires an automated antimeridian stitching step that connects corresponding nodes at matching latitudes across the Date Line with zero-weight topological bridges.
2. **Polar Passage Constraint Masking**: Because high-latitude Great Circle arcs through the Arctic (Northwest and Northeast Passages) are mathematically shorter than equatorial routes ($8,849\text{ NM}$ vs. $9,104\text{ NM}$ via Panama), unconstrained graph pathfinding routes through frozen polar straits. Ingestion and service logic must tag and default-mask polar passages for standard commercial bulk vessels.
3. **Licensing Demarcation & Commitment Go/No-Go Decision**: While the upstream repository declares the European Union Public Licence (EUPL-1.2), the network has composite lineage (Oak Ridge National Laboratory global shipping lanes and Eurostat AIS density tracks) with undocumented third-party chain-of-title. Due to EUPL-1.2 reciprocal copyleft provisions (Article 5), **this investigation recommends a NO-GO decision on committing derived network assets into the Git repository**. Ingestion should operate as an external build or local caching step outside Git.
4. **Zero-Dependency Pure-Python Extraction**: The dataset is distributed as an OGC GeoPackage (`.gpkg`), which is internally an SQLite 3 database. Extraction can be executed using Python's standard library (`sqlite3` and `struct`) without installing native C++ geospatial dependencies (`gdal`, `geopandas`, `fiona`).

All benchmark corridor evaluations performed in this investigation are strictly **exploratory plausibility checks**, confirming topological coherence and sensitivity to canal bypass constraints, rather than certified operational navigation validations.

### 2.2 Historical Lineage, Resolution, and Characterization

Eurostat MARNET is a **generalized maritime shipping-lane network**, not a bathymetric survey or fairway navigation chart. Its documented lineage and characteristics comprise:

1. **Global Base Network**: Derived from the *Oak Ridge National Laboratory (ORNL) CTA Global Shipping Lane Network (c. 2000)*, created by Bob Boundy and Frank Southworth for the U.S. Department of Transportation (Bureau of Transportation Statistics and Maritime Administration). The ORNL network defined generalized commercial shipping corridors between global port regions.
2. **European Coastal and Regional Densification**: Augmented by Eurostat using terrestrial and satellite Automatic Identification System (AIS) vessel traffic density tracks in European and Mediterranean waters.
3. **Canal and Chokepoint Geometry**: Augmented with manual polygon masks (`pass.gpkg`) for 12 international navigation passages and canals.
4. **Available Resolutions**: Distributed in 50 km, 20 km, and 5 km network generalizations. The 50 km generalization (`marnet_plus_50km.gpkg`) provides global macro-corridor coverage with 15,498 line features.
5. **Intended Use**: Designed for macro-level statistical transport modeling (calculating maritime distances between European coastal NUTS regions and global partner ports for Eurostat maritime transport statistics).
6. **Operational Limitations**:
   - **No Bathymetric Depth Soundings**: Does not model water depth, under-keel clearance, or seabed topography.
   - **No Harbor Approaches**: Terminates in deep water (typically 5–30 NM offshore); does not model harbor channels, pilotage fairways, or berth approaches.
   - **No Dynamic Environmental Hazards**: Does not account for weather, sea-state resistance, tidal currents, or seasonal pack ice.
   - **No Regulatory Navigational Separation**: Does not reflect formal IMO Traffic Separation Schemes (TSS) or localized cabotage/traffic management restrictions.

## 4. Legal, Provenance, and Licensing Assessment

### 4.1 Confirmed Upstream License Facts
- **License**: The Eurostat SeaRoute repository root contains an official `LICENSE` file declaring the **European Union Public Licence (EUPL), version 1.2** (14,147 bytes).
- **Scope**: The Maven configuration (`modules/jar/pom.xml`) explicitly declares EUPL-1.2. Under European Commission Decision 2011/833/EU on the reuse of Commission documents, Eurostat asserts EUPL-1.2 over the repository codebase and its bundled GeoPackage assets (`marnet_plus_50km.gpkg`).
- **Attribution (Article 6)**: Downstream distributions must retain copyright notices, license references, and modification statements crediting Eurostat.
- **Copyleft Provisions (Article 5)**: Derivative works, when distributed or communicated to third parties, must remain under EUPL-1.2 or compatible licenses listed in the EUPL appendix (GPL-2.0, GPL-3.0, AGPL-3.0, LGPL).

### 4.2 Unresolved Rights and Provenance Questions
Despite Eurostat's repository-level declaration, several rights questions remain unresolved:
1. **ORNL Lineage Rights**: The base shipping network originates from the Oak Ridge National Laboratory CTA network (c. 2000). While federal agency works prepared by U.S. government employees are in the U.S. public domain under 17 U.S.C. § 105, national laboratory contractor contributions often involve copyright assertions or specific government-purpose licenses. Eurostat documentation cites ORNL research papers but does not bundle a formal chain-of-title or copyright disclaimer from ORNL/US DOT.
2. **AIS Densification Rights**: Eurostat augmented the European network using AIS vessel density data. Eurostat holds authority to license its own compilations, but the upstream documentation does not disclose specific licensing terms or third-party data provider agreements governing the underlying AIS telemetry.
3. **Third-Party Wrapper Discrepancies (`searoute-py`)**: The popular Python wrapper `searoute-py` (Gent Halili) declares `Apache-2.0` in its package metadata while embedding an extracted GeoJSON file of Eurostat's EUPL-1.2 network. Downstream re-licensing of an EUPL-1.2 reciprocal dataset to Apache-2.0 is legally questionable under EUPL Article 5. Pelagos must not rely on `searoute-py`'s Apache claim or third-party packaging.
4. **Copyleft Contagion Risk**: While internal backend execution behind a REST API does not trigger EUPL distribution requirements for SaaS callers, committing a derived binary or JSON network artifact directly into the Pelagos Git repository could blur licensing boundaries with MIT- or proprietary-licensed application code.

## 5. Topological Integration and Technical Feasibility

### 5.1 Graph Construction from Implicit LineString Topology

The GeoPackage stores disconnected LineString features rather than explicit node and edge tables. Graph construction accounts for the transformation from raw features to graph topology as follows:

```
+----------------------------------------------------------------------------------------------------+
|                                GRAPH TRANSFORMATION ACCOUNTING                                     |
+--------------------------------------------------------------------+-------------------------------+
| Raw Input Features in 'type' layer                                 | 15,498 features               |
| Invalid Geometries (un-parseable or corrupt)                       | 0 features                    |
| Closed-Loop Features (start point == end point; self-loops)        | 20 features (0 pass tags)     |
| Parallel-Edge Groups (pairs of nodes with >1 feature)              | 67 pairs (67 duplicate edges) |
| Pass Attribute Conflicts among Parallel Features                   | 0 conflicts (100% consistent) |
| Unique Undirected Edges with Self-Loops Retained                   | 15,431 edges                  |
| Unique Undirected Edges with Self-Loops Excluded (Recommended)     | 15,411 edges                  |
| Unique Navigational Vertices (Distinct Endpoint Coordinates)       | 7,390 unique nodes            |
| Antimeridian Bridging Edges Added Across 180th Meridian            | 12 edges (0.0 NM weight)      |
| Final Operational Graph Edges (excluding self-loops + 12 bridges)  | 15,423 edges                  |
| Final Operational Graph Edges (retaining self-loops + 12 bridges)  | 15,443 edges                  |
+--------------------------------------------------------------------+-------------------------------+
```

1. **Feature Parsing**: Binary GeoPackage geometry headers are unpacked via Python's standard `struct` module to extract WKB LineString coordinates without GDAL.
2. **Vertex Identity**: The initial coordinate $(x_0, y_0)$ defines node $u$; the terminal coordinate $(x_k, y_k)$ defines node $v$. Coordinates are rounded to 6 decimal places ($~0.1\text{ m}$ precision) to ensure deterministic topological hashing.
3. **Edge Weight Calculation**: Edge weights represent WGS 84 ellipsoidal geodesic distance along all intermediate vertices:
   $$W = \sum_{i=0}^{k-1} d_{geodesic}(P_i, P_{i+1}) \quad \text{via } \texttt{pyproj.Geod(ellps='WGS84')}$$
   Distances are computed in meters and converted to international nautical miles ($1\text{ NM} = 1,852\text{ m}$).
4. **Deduplication & Attribute Collision Safety**:
   - Exactly 67 node pairs connect multiple LineString features in `type` (each containing exactly 2 parallel tracks).
   - An exhaustive attribute audit confirms that **exactly 0 parallel groups have conflicting `pass` values** (all 67 pairs either both have `pass=None` or share identical chokepoint strings).
   - Parallel features are safely collapsed by retaining the track with the minimum geodesic weight, discarding exactly 67 redundant features without corrupting or losing any chokepoint tags.
5. **Self-Loop Treatment ($u == v$)**:
   - The dataset contains exactly 20 closed-loop features where the starting coordinate equals the terminal coordinate.
   - None of the 20 self-loops carry chokepoint tags (`pass=None`), and all 20 nodes connect to other valid edges in the network.
   - Because self-loops have positive length ($W > 0$), Dijkstra pathfinding between distinct origin/destination pairs will never traverse them.
   - *Recommendation for D9.4*: Ingesting code should explicitly filter out self-loops ($u \ne v$), yielding a clean simple graph of **15,411 base edges** (**15,423 edges** after antimeridian bridging) across **7,390 nodes**.
6. **Directionality**: Because commercial sea lanes in MARNET represent bi-directional fairways, edges are loaded into an undirected graph (`nx.Graph`).

### 5.2 Antimeridian Bridging (The Pacific Disconnection Issue)

In planar GIS datasets, spatial features are severed at the 180th meridian to prevent rendering artifacts on 2D projections:
- West of the Date Line: Nodes terminate at longitude $+180.0^\circ$.
- East of the Date Line: Nodes terminate at longitude $-180.0^\circ$.

Because $+180.0 \ne -180.0$, graph loaders treat these as separate nodes, severing trans-Pacific connectivity and causing trans-Pacific queries (e.g. Seattle to Yokohama) to route across the Atlantic and Indian Oceans ($17,388\text{ NM}$).

#### Bridge Generation and Mathematical Validity:
- **Node Analysis**: In `marnet_plus_50km.gpkg`, exactly 15 nodes lie at $+180.0^\circ$ and 15 nodes lie at $-180.0^\circ$.
- **Exact Latitudinal Parity**: Exactly 12 node pairs share **identical latitudes** ($d_{lat} = 0.000000^\circ$) across the Date Line:
  $-60.0^\circ, -50.0^\circ, -40.0^\circ, -30.0^\circ, -20.0^\circ, 0.0^\circ, +10.0^\circ, +20.0^\circ, +30.0^\circ, +40.0^\circ, +62.1^\circ, +70.0^\circ$.
- **Physical Weight Validity**: Because $(+180.0^\circ, \phi)$ and $(-180.0^\circ, \phi)$ represent the exact same physical coordinates on the Earth's surface, the geodesic distance between them is **$0.0\text{ NM}$**. Assigning a weight of $0.0$ to these bridging edges is mathematically exact.
- **Duplicate and Invalid Connector Prevention**:
  - Bridging requires strict 1-to-1 matching: a node at $+180.0^\circ$ connects only to a node at $-180.0^\circ$ if $|lat_1 - lat_2| < 10^{-5}$ degrees.
  - Cross-latitude connections are prohibited, preventing fictitious diagonal paths.
  - Idempotent insertion into `nx.Graph` ensures exactly 12 unique undirected bridge edges are created.
  - The 3 unmatched boundary nodes on each side terminate near islands (e.g. Fiji/Tonga) where the upstream network did not extend across the meridian.

#### Topological Connectivity vs. Real-World Operational Navigability:
> [!WARNING]
> **Topological connectivity does NOT prove operational navigability.**
>
> With antimeridian bridging, 100% of the 7,390 nodes belong to a single connected component. However, mathematical graph connectivity proves only that a sequence of line segments exists between vertices. It does **not** prove:
> - That specific commercial vessels have safe draft clearance or under-keel margin.
> - That harbor entrances connect to the deep-water grid (MARNET nodes remain 10–30 NM offshore).
> - That paths obey Traffic Separation Schemes (TSS), collision regulations (COLREGS), or cabotage laws.
> - That routes avoid severe weather, ice fields, or restricted military zones.

### 5.3 Polar Route Masking

Because Great Circle arcs are shortest at polar latitudes, unconstrained Dijkstra pathfinding through MARNET selects the Canadian Arctic Archipelago (`northwest` passage, $8,849\text{ NM}$) between the Atlantic and Pacific rather than the Panama Canal ($9,104\text{ NM}$).

- **Ingestion Requirement**: Commercial routing policies must classify `northwest` and `northeast` passages as restricted, applying prohibitive weights ($10^9$) by default unless the request explicitly specifies an ice-class polar transit policy.

## 8. Proposed Ingestion Architecture and Pipeline Design

### 8.1 Zero-Dependency External Ingestion Script (`scripts/ingest_marnet.py`)

In compliance with project nonfunctional requirements ([REQ-NFR-DCT-001](../requirements/nonfunctional-requirements.md)) and the NO-GO recommendation on committing data to Git, ingestion will operate as an external build step:

```
+----------------------------------------------------------------------------------------------------+
|                                    PROPOSED INGESTION PIPELINE                                     |
+----------------------------------------------------------------------------------------------------+
| 1. Download: Fetches marnet_plus_50km.gpkg and pass.gpkg via HTTPS into .cache/pelagos/routing/   |
| 2. Decode:   Queries SQLite 'type' table, unpacks WKB LineStrings via pure Python struct module.   |
| 3. Stitch:   Identifies +-180.0 deg boundary nodes and inserts 12 zero-weight antimeridian bridges.|
| 4. Weigh:    Calculates WGS 84 geodesic lengths via pyproj.Geod(ellps='WGS84').                    |
| 5. Output:   Serializes to Git-ignored local data path: data/marnet_network.json.                  |
| 6. License:  Writes full EUPL-1.2 license notice and Eurostat attribution to data directory.       |
+----------------------------------------------------------------------------------------------------+
```

### 8.2 Dual-Mode Engine Design in `backend/pelagos/routing/`

The runtime routing engine will support dual-mode execution:
- **`mode="prototype"`** (Default for unit tests and CI): Loads lightweight `fixtures/sea_lanes.json` (<2 ms). Returns `route_method="prototype_test_network_graph"` with non-operational disclaimers.
- **`mode="operational"`**: Loads local `data/marnet_network.json` (~50 ms startup). Returns `route_method="marnet_shipping_lane_network"` with EUPL attribution. If the data file is absent, the engine falls back gracefully or returns explicit setup guidance without fabricating geometry.
- **Safety Safeguard**: Both modes strictly reject disconnected or inland coordinates with `status="unsupported_route"` or `status="invalid_input"`, maintaining zero straight-line fallback.

4. **Antimeridian Polyline Normalization for Visualization (D9.4 Acceptance Requirement)**:
   - The current serialization schema in `backend/pelagos/routing/schemas.py` defines `geometry` as a single contiguous array (`List[List[float]]`). Tracing path serialization shows that an antimeridian bridge edge emits adjacent vertices `[-180.0, \phi]` and `[180.0, \phi]`.
   - In 3D space (`Cesium.SceneMode.SCENE3D`), `Cartesian3.fromDegrees(-180, \phi)` and `Cartesian3.fromDegrees(180, \phi)` evaluate to the exact same $(X, Y, Z)$ point ($0.0\text{ m}$ Euclidean offset). However, in 2D map views, Columbus View (`SCENE2D`/`COLUMBUS_VIEW`), and planar ground-clamping tessellators, a contiguous line between $-180^\circ$ and $+180^\circ$ draws an unwanted horizontal line wrapping $360^\circ$ across the entire globe.
   - *Requirement for D9.4*: The routing API or frontend adapter must implement RFC 7946 antimeridian cutting (splitting the route into disjoint segments or `MultiLineString`) or continuous longitude unwrapping to guarantee clean visual rendering across the International Date Line.
